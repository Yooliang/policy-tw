# 實作規劃：加權共識（票數預算 ＋ −2～+2 的票權重 ＋ 總分制）

狀態：**規劃，待審。** 2026-09-21。設計討論見 `PROPOSAL-jev-vote-budget.md`。
這份牴觸 2026-09-19 的「門檻＝型別風險 × 來源等級」與「兩票反對＝爭議」，
落地時要在 `docs/DECISIONS.md` 寫「更正」，不是默默覆蓋。

---

## 1. 現在的機制與它的三個毛病

```
門檻 = 型別風險 × 來源等級（2／3／4／6／8）
       系統票 supported −1（最少 1）／not_supported +1
通過 = agree ≥ 門檻 且 disagree ≤ 1
爭議 = disagree ≥ 2
```

**毛病一：矩陣看不到「這一筆好不好查證」。** 它只看型別與網域。中選會名單上白紙黑字的
參選登記要 6 票，而一筆來源證明不了是誰說的政見只要 2 票。實測（2026-09-21）：

| 貢獻 | 現行門檻 | Jev 逐維度評出來的 |
|---|---|---|
| 某筆 candidacy，有完整登記名單、官方來源 | **5 票** | 3 票 |
| 某筆 policy，Jev 以 1.00 信心說「證明不了是這個人說的」 | **2 票** | 5 票 |

**毛病二：票沒有輕重之分。** 2026-09-21 實例（蘇輝湟）：一張**沒打開來源**的 agree
蓋過一張**附了反證**的 disagree，因為規則只數「幾張」。

**毛病三：門檻降到 1 時，一張反對票形同不存在。** 「達標且反對 ≤1 就通過」是配著
4～8 票的門檻設計的；系統票 −1 把門檻壓到 1 之後，這條規則等於讓單張同意票否決反對票。

## 2. 目標機制

```
目標分數 = max(型別地板, 2 − 中選會折扣 + 風險加成)
每一票   = −2 ～ +2（Jev 評那一票的證據）
累計 ≥ 目標   → verified → 落庫
累計 ≤ −目標  → disputed → 開裁決任務
其餘         → pending，繼續等票
```

**分工**：票數預算評**提交本身**的風險（要幾分才夠）；票權重評**那一票**的證據（移動多少）。

### 2.1 風險加成（已實作，影子模式運行中）

`_shared/vote-budget.ts`：每一種 `contribution_type` 有自己的風險維度，
Jev 對每一維給機率，**≥0.80 的維度各加一票，封頂 5**。判不出來算命中。

為什麼是多維度而不是 0～5 多選一：`policy` 的「來源只提到主題」與「跟既有疑似重複」
不在同一條軸上——一筆可以同時是這兩種，而 argmax 只會留下一個。**風險要疊加。**

### 2.2 票權重（本次要做）

| 分數 | 什麼樣的票 | 誰判定 |
|---|---|---|
| **+2** | 附了獨立的第二來源，而且那個來源直接支持宣稱 | Jev（現有的 `second_source`／`judge` 就是在做這件事） |
| **+1** | 打開了提交者附的來源、逐欄核對過、理由具體 | 規則：有 `note` 實質內容 |
| **0** | 理由是套語，或只說「看起來沒問題」 | 規則：#129 的 `note_too_thin`／`note_repeated` 判準 |
| **−1** | 反對，理由具體但附不出反證 | 規則 |
| **−2** | 反對，而且附了**直接矛盾**的反證 | Jev（同 `second_source`，verdict 為 not_supported） |

**Jev 判不出來時算 ±1，不是 ±2**：往「一票就是一票」倒，不要因為看不懂就給滿分或零分。

### 2.3 三個護欄

1. **下界是必要的，不是選配。** 單邊門檻不會終止——一筆停在 −1 的東西不夠正不能通過、
   不夠負不能進裁決，會永遠佔著驗證池。所以 `≤ −目標` 必須觸發爭議。
2. **高風險型別另外要求人數。** `merge_politician`／`candidacy`／`removal` 的分數
   不得由單一來源 IP 湊足，至少要 2 個不同來源 IP。分數高不等於看過的人多。
3. **權重要讓代理看得見。** 回應必須寫「你這一票記為 +1，因為沒有附獨立的第二來源」。
   看不見就學不會，而學不會就沒有人會去找第二來源。

## 3. 落地步驟

### 階段 0（已完成）
- `vote-budget.ts`：11 種型別的風險維度、`computeVoteBudget`
- `POST /system-one?action=vote_budget`：影子模式，只寫 `jev_decisions` 不套用
- 線上實測 2 筆，成本 US$0.00004～0.0002／筆

### 階段 1：批次建立佐證（唯讀，不改任何行為）
對全站 pending 的貢獻跑一次 `vote_budget`，寫進 `jev_decisions`。
目的有二：**看真實分布**；以及讓代理領到驗證項時看得到「系統認為這筆的風險在哪幾維」。

- 成本：1,400 筆 × US$0.0002 ≈ **US$0.3**
- 風險：無，純寫入 `jev_decisions`
- 出口條件：分布看起來合理（不是全部 0 分或全部滿分）

### 階段 2：票權重也跑影子模式
每一票進來時照 §2.2 算出權重，寫進 `contribution_votes.weight_shadow`，**不影響計票**。
同時把「累計分數」算出來記錄，與現行的 `agree_count ≥ 門檻` 並行比較。

- 需要：`contribution_votes` 加 `weight_shadow SMALLINT`、`weight_reason TEXT`
- 出口條件：**兩套機制的結論在多數案子上一致**；不一致的那些，人工看過之後
  認同新機制的判斷（而不是舊的）

### 階段 3：切換
`contribution_apply_consensus` 改用總分。舊的 `agree_count`／`disagree_count` 保留
（顯示與稽核仍要用），但不再決定狀態。

- 必須同時上：下界觸發爭議、高風險型別的人數下限、回應顯示權重與理由
- 協議升版，`skill.md` 改寫「需要幾票」那一節成「需要幾分、你的票值幾分」

### 階段 4：回收
拆掉 `AGREE_THRESHOLDS` 矩陣與「兩票反對＝爭議」的分支。
`docs/DECISIONS.md` 寫「更正」，說明取代了哪兩條舊裁決。

## 5. 這個規劃可能錯在哪（請審查者優先看這幾點）

1. **Jev 評「票的證據」沒有校準資料。** `second_source` 只有 10 筆紀錄。階段 2 的影子模式
   就是為了補這個，但如果 Jev 在這個問題上系統性偏頗，影子期未必看得出來。

2. **總分制對「沉默」的處理沒有定義。** 一筆得到 +1 之後再也沒有人投票，它會一直是 pending。
   現行機制也有同樣問題，但總分制讓它更可見。要不要加時間維度（例如 N 天後降低目標分數）？
   **我傾向不要**——那會變成「等久了就會過」，但沒有更好的答案。

3. **權重會不會讓代理只做容易的？** 原本擔心代理挑容易找第二來源的題目，
   但**任務是伺服器分發的、代理選不了**，所以這個顧慮不成立（2026-09-21 使用者指正）。
   剩下的風險是：代理可能為了拿 +2 而硬找第二來源，找到牽強的也算。
   `judge` 會擋掉同網域與轉載，但擋不掉「主題相關但證明力弱」的來源。

4. **目標分數是 Jev 定的，票權重也是 Jev 定的。** 同一個判斷者站在天平兩端。
   Jev 若系統性高估風險，目標會變高；若系統性低估票的證據，分數會變低——兩個偏差同向疊加。
   這是這個設計最根本的疑慮，我沒有好的解法，只有「影子期兩邊分開看」。

5. **11 種型別的維度是我寫的，沒有經過使用者逐條確認。** 維度選錯會讓整個機制歪掉，
   而且歪得很安靜。審查時請特別看 `_shared/vote-budget.ts` 裡的維度表。

---

## 6. 明確不做的

- **不動 Jev 的 0.95 門檻**（2026-09-19 裁決，使用者明講不降）。維度閾值 0.80 是另一件事：
  它是「這一維算不算命中」，不是「Jev 的答案算不算數」。
- **不讓 Jev 擋票。** 它只調整權重，不拒收。代理投的票一定會被記下來，
  差別只在移動多少分——避免「我以為我投了票，其實被吞掉」。
- **不批次改既有資料。** 切換後既有的 pending 依新制重算，但已落庫的不回溯。

# 計畫：政見的 Markdown 檢視（人物／縣市／分類，之後加「縣市＋主題」）（2026-10-07）

> **狀態：規劃中，沒有任何程式。** 維護者 10-07 要求先規劃再動手；本檔只提方案與待裁項。數字是 10-07 用公開 anon key 唯讀查正式庫得來（`policies` 沒被移除的 1,198 筆；2026 屆有參選紀錄的人 1,273 位、其中 292 位名下有政見、共 1,111 筆）。

## 0. 定位

維護者的話：**「你們需要事實，我們有，整理好了，來讀吧。」** 正見要做 AI、記者、研究者能直接引用的事實來源。Markdown 檢視是這句話的實體：一個網址就是一份整理好的、帶出處與時間的純文字，貼給 AI、丟進 NotebookLM 都能直接用。

原則（沿用 `CLAUDE.md` 主線守則）：

- **讓資料自己說話**：只列事實、標籤（未說明／未調查／推定／結果待補）與出處；不評價、不排名、不放排序方式與方法論的說明文字（規則寫進 DECISIONS）。
- **網址保持**：現有網址一個都不動；.md 是新增的另一種呈現，**HTML 網址加 `.md` ＝ 它的 Markdown 版**。
- **資料走流程**：「主題」這種新分類的資料，不由我們寫 migration 灌，走代理貢獻＋投票（第 3 節）。
- 只用 anon 讀資料；第一期不新增 migration（第 8 節的讀取計數除外，要先問）。

## 1. 目標

1. 第一期：政見依**人物／縣市／分類**各有一份 Markdown 摘要，可直接開、可貼進 AI。
2. 之後：用**縣市＋主題**組合拿到一個 .md 網址，例如「台南 育兒」→ `/data/台南市/育兒.md`。
3. 之後：自由文字（「台南 育兒」）能解析成上面的網址，不靠即時 LLM。
4. 給 AI 的入口、授權、新鮮度、穩定網址承諾（第 9 節）。

## 2. 網址設計

### 2.1 建議

| 內容 | 網址 | 說明 |
|---|---|---|
| 人物 | `/politician/<id>.md` | 就是人物頁 HTML 網址加 `.md` |
| 縣市（某屆） | `/election/<屆>/<縣市>.md` | 縣市頁 HTML 網址加 `.md`，例 `/election/2026/台南市.md`（`<屆>` 沿用 `lib/election-route.ts` 的 `electionSegment`：舊三屆是年份、新增的選舉是 `election_key`） |
| 縣市（最新一屆） | `/data/<縣市>.md` | 短網址，301 到最新一屆的縣市 .md（最新一屆看 `election_date`，不從 id 推年份） |
| 分類 | `/category/<分類>.md` | 分類＝`categories` 表固定 19 類；全國、依縣市分組 |
| 縣市×分類 | `/data/<縣市>/<分類>.md` | 例 `/data/台南市/交通建設.md` |
| 縣市×主題（之後） | `/data/<縣市>/<主題>.md` | 例 `/data/台南市/育兒.md`；主題詞彙表見第 3 節 |
| 全國×主題（之後） | `/data/全國/<主題>.md` | 沒指縣市時的退路 |
| 索引 | `/llms.txt`（已存在，靜態）＋ `/data/index.md`（動態概況） | 見第 9 節 |

`/data/<縣市>/<名稱>.md` 的第二段解析順序：**分類全名 → 主題全名 → 404 並列出可用的**。分類名與主題名在詞彙表建立時就要求不得重名（守門測試擋，而且要照「守門測試要還原驗證」做一次還原確認）。

**副檔名決定格式，同一路徑可有 .md／.json**（例如 `/data/台南市/育兒.md`、之後 `/data/台南市/育兒.json`）；所以縣市×分類／主題用 `/data/` 前綴而不是 `/md/`（維護者 10-07 裁示）。人物、縣市、分類仍是各自 HTML 網址加副檔名。

### 2.2 編碼與慣例

- 中文名走 percent-encoded UTF-8（`encodeURIComponent`），跟現有縣市頁、鄉鎮頁、`canonicalPath` 同一種寫法。
- 地名寫法用資料庫的 `台`（台南市），輸入 `臺南市` 一律 301 到 `台`（`lib/region-name.ts` 已有同一套）。
- 縣市 .md **不需要**像 HTML 縣市頁那樣搬成十六進位 ASCII 路徑（`region-path.js`）——那是因為 Firebase 對中文目錄比對沒保證；.md 全由 Worker 現場回，不經 Firebase 檔案系統。
- 結尾 `/` 與大小寫：去尾斜線；`.md` 只認小寫；`.MD` 不處理。

### 2.3 路徑式 vs 查詢式

| | 路徑式 `/data/台南市/育兒.md` | 查詢式 `/data?city=台南市&topic=育兒` |
|---|---|---|
| 快取 | 一個網址一份快取，命中率高；Cache API 與 Cloudflare 都以完整網址為鍵 | 參數順序、多餘參數都會產生不同的鍵，要自己正規化 |
| 引用與書籤 | 乾淨、可貼、可列進 llms.txt | 容易被貼壞、被追蹤參數污染 |
| 慣例 | 與 09-30、10-05 把縣市、鄉鎮從查詢字串改成路徑（搜尋引擎不當獨立頁）的方向一致 | 與那次的方向相反 |
| 自由輸入 | 不適合 | 適合——所以只在**入口**用：`/data/search?q=台南 育兒` → 解析成路徑後 302 過去；解析不了回 404 的 Markdown（第 5 節） |

**建議：路徑式為唯一正式網址，查詢式只當入口、一律轉成路徑式。** 舊網址不動：本計畫沒有任何既有網址被改。

## 3. 「主題」從哪來

### 3.1 為什麼現有欄位不夠

- `policies.category`：固定 19 類，粒度太粗。「育兒」散在社會福利（94）、都市發展與住宅（18，婚育宅）、醫療衛生（16）、教育文化（13）等類——**育兒關鍵字命中的 157 筆裡，63 筆（40%）類別不是社會福利**。只查分類會漏掉四成。
- `policies.tags`：自由填、沒有正規化（`lib/issue-tags.ts` 的註解寫得很清楚：92 個相異標籤一堆是人名、年份、口號、來源）。2026 屆 1,111 筆只有 74 筆有 tags（6.7%），相異標籤共 159 個、最常見的才 6 筆。**不能拿來當主題。**

### 3.4 資料走流程：系統挑候選、代理判斷、投票上線

不寫 migration 灌資料，也不讓程式的關鍵字結果直接上線：

1. **候選由系統挑**：用 `lib/topics.ts` 的同義詞對每筆政見算候選主題（關鍵字＋所屬分類），這是候選，不是結論。
2. **派任務給代理判斷**：一位人物名下沒標主題的政見打包成一個任務（2026 屆約 292 件，每件平均 3～4 筆政見），任務附候選與政見原文，代理回「這筆屬於哪 0～2 個主題、依據哪一句」。
3. **投票上線**：沿用現有共識（3 分達標、同 IP 一票、系統票）。
4. **後續維護**：新政見上線時自動帶候選派任務；詞彙表加新主題時，只對**該主題候選非空**的政見補派。

兩個做法比較：

| | 新貢獻型別 `policy_topic`＋新表 `policy_topics` | 沿用既有 `correction` 改 `policies.tags` |
|---|---|---|
| 結構 | 乾淨：一列一個（政見、主題、依據），可查可算，可有「判定為無」 | 寫進自由陣列，又回到未正規化的老問題 |
| 成本 | 要 migration＋四處清點（DB CHECK `contributions_contribution_type_check`、TS `CONTRIBUTION_TYPES`／`TASK_TYPES`／`SUGGESTED_TYPE`、`public/skill.md`、`lib/task-labels.ts`；漏 CHECK 的話交件全被擋而測試全綠，09-20 踩過）；協議版號升一號 | 不用新型別 |
| 與既有規則 | 先例：`policy_elements`（政見三要素，#364）——「沒有列＝未調查、`stated=false`＝未說明」同一套語意，主題也要分「未調查」與「查過、不屬於任何主題」 | `tags` 的正規化是 `issue-tags.ts` 註解寫明的「Jev 的事，另案」 |

**建議新型別＋新表**（第二期的主要工作量）。這會動協議與 migration，**開工前要維護者點頭**；判斷任務的量（約 292 件×3 票）也要先看佇列容量。主題上線前，.md 與 HTML 都不顯示主題。

## 4. 內容規格（第一期）

每份 .md 一律從固定中繼資料開頭（YAML front matter，第 9 節詳述），接著：

- **人物**：姓名、政黨、參選紀錄（屆別、職位、選區、參選狀態／結果）、任期（讀任期表 `offices`；職稱只能來自它，規則見 `lib/politician-office.ts`）、政見清單（類別、標題、狀態、進度、提出日期、最後更新、出處網址）、HTML 網址。
- **縣市**：該縣市各選舉（以最新一屆為主，含 2026）候選人一覽＋各人政見（欄位同上）。
- **分類**：依縣市分組列政見（人物、標題、狀態、出處）。量大（交通建設 2026 屆約 196 筆）時只列 2026 屆與現任者，並註明完整清單在哪個 .md／HTML。
- 狀態用資料庫值對應的中文標籤（競選承諾／提出／進行中／已實現／滯後／未達成），**不評價**；沒有出處的寫「出處待補」。
- **排序**：不照網頁預設的「最近更新」。原因：網頁預設排序每分鐘都會變（卡在李四川的事故就是這個，見 `ElectionPage.vue` 註解），不利快取與引用，而且「最前面」對候選人有曝光差。.md 一律**姓名筆畫**（網頁已有的中性選項，`lib/region-name.ts` 的 `compareRegionName`），同組內政見依提出日期、再依 id。這跟「依現有網站排序規則」有出入，列為待裁項 1。

## 5. 自由文字查詢（第三期）

例：`/data/search?q=台南 育兒`。**不靠即時 LLM**，純規則：

1. 正規化：全形轉半形、`臺→台`、去標點、空白切詞。
2. **縣市**：22 縣市全名＋簡稱表（台南→台南市、北市→台北市…）；最長比對優先。
3. **主題**：`lib/topics.ts` 同義詞表（育兒＝托育＝托嬰＝生育補助＝育兒津貼＝幼兒園…）；也吃分類全名。最長比對優先，剩下的詞丟掉（但回應裡列出「未使用的詞」）。
4. 結果：
   - 縣市＋主題（或分類）都有 → 302 到 `/data/<縣市>/<名稱>.md`
   - 只有縣市 → 302 到 `/data/<縣市>.md`；只有主題 → 302 到 `/data/全國/<主題>.md`
   - 兩個都沒有、或有多個縣市 → 回 **404、`text/markdown`**，內容是「沒認出來」＋縣市清單＋主題清單（連結），這份說明是給 AI 讀的，所以寫得機械、完整。
5. 同義詞表的維護：加在 `lib/topics.ts`；守門測試要求每個同義詞指向存在的主題、不得同時指兩個主題，並且要做一次還原驗證（拿掉一條同義詞確認測試會紅）。
6. 查不到的詞（例如「育兒」之外的新說法）記不記？建議不另開表；Worker 已有的 `ai_reads` 只記計數。要累積「沒認出來的詞」另案，先不做。

## 5b. 實作方式比較

| | Worker 動態（建議） | SSG 預產 |
|---|---|---|
| 規模 | 現場算，網址數不限 | 人物約 1.6 萬＋縣市＋分類＋縣市×主題：又是「16k 頁、12 分鐘建置」，正是 09-23 搬去邊緣 SSR 要擺脫的 |
| 新鮮度 | 當下的資料，Cache API 10 分鐘 | 要等下一次建置（連續合併還會排隊） |
| 與 HTML 一致 | 共用 `lib/ssr/loaders.ts` 的資料載入與 `mapPolicy`／`mapPolitician`，同一份資料、同一個過濾（`removed_at`、`merged_into`、`policy-visibility`） | 預渲染快照與 HTML 同源，但 .md 要另外建一套產檔流程 |
| 成本 | Worker 請求（免費額度每日 10 萬，要看 AI 讀取量）＋ Supabase 每份約 2～4 個查詢 | 建置時間 |
| 風險 | 查詢量大時打到 Supabase；縣市頁一次要撈一縣的候選人與政見 | 檔案多、部署慢 |

**建議 Worker 動態**，每份 .md 的組字放在 `lib/md/*.ts`（純函式、不碰 Worker API，隨 `pnpm build:ssr` 一起進 `dist-ssr/`），`cloudflare/ssr-worker.js` 只負責路由、快取、標頭。每份 .md 的查詢預算（都有界、遵守 `query-bounds`）：

- 人物：`politicians_with_elections`（1）＋`policies_with_logs`（1）＝2 個
- 縣市：該縣該屆候選人（沿用同選區 RPC 的做法）＋名下政見（`in` 一批 id、必要時分批）＝約 2～3 個
- 分類／縣市×分類／縣市×主題：政見（依 `category` 或 `policy_topics`）＋對應人物 ＝ 2 個

**快取**：沿用 `renderPage` 的做法（Cache API、10 分鐘過期後先回舊的再背景重算），回應標頭 `Cache-Control: public, max-age=0, s-maxage=600, stale-while-revalidate=3600`；`POST /__purge`（既有）要能清 .md 變體——政見落庫時打的 purge 清單要把 `<頁>.md` 一併帶上，否則最多舊 10 分鐘（可接受，不阻擋第一期）。

**收錄與標頭**：

- 所有 .md：`Content-Type: text/markdown; charset=utf-8`、**`X-Robots-Tag: noindex`**（不跟 HTML 搶搜尋排名；AI 仍可讀）。**`robots.txt` 不得 Disallow `.md`**，否則爬蟲讀不到 noindex 反而可能把網址收進索引。
- HTML 頁（人物、縣市、政見、脈絡）`<head>` 加 `<link rel="alternate" type="text/markdown" href="….md">`，在 `composables/usePageHead.ts`。
- `/llms.txt` 不加 noindex。
- 只有 **正見.tw** 保證可用；直接打 `policy-tw.web.app/politician/<id>.md` 會被 `firebase.json` 的 rewrite 送到 `app.html`，不處理，文件寫明。

## 8. 讀取量怎麼計

現況：`cloudflare/ai-reads.js` 依 UA／Referer 分類，Worker 批次寫 `ai_reads_daily`；`path_type` 白名單（`politician`、`policy`、`election`、`skill`、`llms`、`sitemap`、`other`）同時寫在**表的 CHECK、`ai_read_hit()`、`ai_read_hits()` 三處**（`20260923000008`、`20260924000001`）。

- `.md` 目前會被歸到 `other`（路徑不符任何一類）：能計數，但看不出是 `.md` 還是別的，也看不出是人物還是分類。
- 建議第一期加 `path_type = 'markdown'`（`politician_md`／`region_md`／`category_md` 三類更好），要一支小 migration 改三處白名單（先例：`20260929000013` 加 `agent_protocol`）。**這是第一期唯一的 migration，要先問維護者**；若不同意，退路是先全進 `other`。
- `llms.txt` 已有 `llms` 類，不用改。
- 現有分類只認「已知 AI 的 UA 與 AI 服務的 Referer」。NotebookLM 或使用者貼網址進 AI 工具時，UA 不一定認得——這種讀取數不到。建議在同一支 migration 加一個 `kind = 'unknown_md'`，把「不認得 UA 但讀的是 .md」也記一筆（.md 本來就不是給一般瀏覽器開的，所以算得進來）。是否要做列為待裁項 3。
- 計數只記每日計數（代理、類別、頁種），不記網址與 IP——不變。

## 9. 給 AI 的入口（維護者定位的具體化）

### 9.1 `llms.txt` 與 `llms-full.txt`

- **`/llms.txt`**：repo 的 `public/llms.txt` 已存在（站點簡介、引用格式、協議入口）。第一期改寫：加上 .md 網址規則、22 縣市與 19 分類的 .md 連結清單（靜態，因為清單固定）、人物 .md 的網址格式、`/data/index.md`。已有的引用格式與「讀資料時要知道的」保留。
- **`llms-full.txt`：建議不做單一大檔。** 估算 2026 屆 1,111 筆政見×約 300 字元≈ 35 萬字元，超過多數模型一次可吃的量，也變成每次都要重算的大檔。縣市與分類 .md 本身就是分塊：要整包的人可以把 22 個縣市 .md 當 22 份來源丟進 NotebookLM（單份約 20～50 KB）。若維護者堅持，之後可做成 `/data/index.md` 的附錄清單，不是新檔。
- `/data/index.md`（動態）：全站概況——資料截至、各屆候選人與政見筆數、縣市與分類 .md 清單。取代「每個人一個連結」（1.6 萬個不列進索引）。

### 9.2 每份 .md 開頭的固定中繼資料

YAML front matter，欄位固定、不隨頁面種類增減（缺的填 `null`），機器好解析：

```yaml
---
title: 台南市 2026 地方選舉候選人與政見
source: 正見.tw
url: https://xn--2lw665d.tw/election/2026/%E5%8F%B0%E5%8D%97%E5%B8%82.md

generated_at: 2026-10-07T10:42:11+08:00   # 這份 .md 產生的時間
data_as_of: 2026-10-07T09:58:02+08:00     # 收錄的資料裡最新一筆變動時間（取 policies.updated_at 的最大值）
license: CC BY 4.0
license_url: https://creativecommons.org/licenses/by/4.0/
cite: 資料來源：正見（正見.tw）https://xn--2lw665d.tw/election/2026/%E5%8F%B0%E5%8D%97%E5%B8%82（資料更新：2026-10-07）
```

### 9.3 授權、標示、穩定網址、新鮮度

**授權：已經定了，不是新問題。** `LICENSE-DATA.md` 與 `public/llms.txt` 已寫資料依 **CC BY 4.0**。只剩下面幾項要維護者看：

- 待裁 4：`LICENSE-DATA.md` 的標示網址寫的是 `policy-tw.web.app`，與 `llms.txt`（正見.tw）不一致；要改成「正見.tw」＋punycode 網址（引用時**標「正見.tw」與原始出處**）。
- 待裁 5：.md 裡有第三方來源（選舉公報、新聞）的連結與標題：CC BY 4.0 涵蓋我們整理的資料與欄位，不涵蓋原始出處本身的著作權；要在 .md 固定聲明一行「原始出處的權利歸原發布者」。
- 每條政見附出處網址；沒有出處的明講「出處待補」，不省略。

**穩定網址承諾**（建議寫進 `docs/DECISIONS.md` 與 `llms.txt`）：

1. HTML 網址加 `.md` 的對應關係永不改；要改就先 301，不會 404。
2. front matter 的欄位只增不改名、不刪；不相容的改動升 `format_version`，舊版至少留 90 天（待裁項 6：留多久）。
3. 縣市、分類、主題 .md 的網址一旦對外公布就保留；主題改名時舊名留作同義詞。

**新鮮度**：

- 每筆政見一行帶「最後更新」（`policies.updated_at`，timestamptz；快照沒帶才退回 `last_updated` 的日期）。
- 每份 .md 的 `data_as_of` 取收錄資料的最大 `updated_at`；全站的資料截至在 `/data/index.md`。
- 快取最多舊 10 分鐘（purge 接上後更短），文件寫明。

### 9.4 進階通道（後期，不做）

- `.json`：同網址換副檔名，內容與 .md 同一份資料、欄位同 front matter。**只在 .md 站穩、有人要時才做**，因為資料已經能經 Supabase 公開 REST 讀（`skill.md` §7）。

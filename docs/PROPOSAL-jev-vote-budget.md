# 提案：票數改由 Jev 決定（基本 2 票 ＋ 中選會 −1 ＋ Jev 0～5）

狀態：**影子模式，排程中（2026-09-23 起）。** 使用者 2026-09-21 提出方向，本文補上實測數字與風險；09-21 當晚裁示目標一律 3、不接上（見 DECISIONS），端點留成影子模式但沒有排程，兩天只累積 2 筆。09-23 小良哥裁示排進排程（`system-one?action=vote_budget_sweep`，每 10 分鐘 20 筆，只記錄不套用），累積分布後對照實際結果再決定閾值與要不要接上。
牴觸 2026-09-19 的「門檻＝型別風險 × 來源等級」，若採用要在 `docs/DECISIONS.md` 寫「更正」。

## 現在的問題

門檻是一張 `型別風險 × 來源等級` 的矩陣（2／3／4／6／8），系統票再 ±1。結果：

- 中選會名單上白紙黑字寫著的參選登記，要 **6 票**才上線
- 全站 **1,400+ 筆** pending 塞著，驗證票是最稀缺的資源
- 反過來，有效門檻掉到 1 時，**一張帶反證的反對票會被一張同意票蓋過去**（2026-09-21 蘇輝湟那筆實例）

矩陣是靜態的：它看「型別」與「網域」，看不到「這一筆到底好不好查證」。

## 提案的機制

```
門檻 = max(型別地板, 2 − 中選會折扣 + Jev 加成)
```

- **基本 2 票**，每一種任務都一樣（取代整張矩陣）
- **中選會折扣（0 或 −1）**：Jev 獨立判斷「這一筆有沒有中選會的結構化資料佐證」
- **Jev 加成（0～5）**：扣完之後，Jev 再給一個風險加碼

Jev 因此要有**兩個輸出**，分開算，不要混成一個分數。

## 實測：Jev 現在講得出什麼

`jev_decisions` 的 `source_support` 共 1,709 筆：

| 判定 | 筆數 | 佔比 | 信心分布 |
|---|---|---|---|
| `cannot_tell` | **957** | **56%** | 機率一律 0 |
| `supported` | 750 | 44% | ≥0.95 有 452、0.80–0.95 有 245、<0.80 有 53 |
| `not_supported` | **2** | **0.1%** | — |

**兩個發現決定了這個提案該怎麼落地：**

**一、Jev 有 56% 的時候說「我看不出來」。** 在提案裡那是**最常見的情況**，所以 `cannot_tell` 對應到什麼值，比 0～5 的上限重要得多。**不能是 0**——那等於「Jev 看不懂就 2 票放行」。建議 `cannot_tell → +1`（回到 3 票，接近現行一般資料的門檻）。

**二、Jev 幾乎從不說「不支持」**（1,709 筆裡 2 筆）。它是**確認者不是過濾器**：能讓查得到的東西快速通過，不能指望它攔下編造的東西。所以：

- 中選會折扣有根據——那是「我確認了」，Jev 做得到
- **0～5 的加成沒有校準資料**。它要回答的是「這一筆有多需要多看幾眼」，那是風險問題不是來源問題，Jev 從來沒被問過，我們手上沒有任何它在這個問題上的表現紀錄

## 所以建議分兩段上

**第一段（有根據，可以做）**：基本 2 票 ＋ 中選會 −1。這一段的效果可預測：中選會查得到的參選登記從 6 票降到 1～2 票，`1,400+` 的積壓會明顯鬆動。

**第二段（要先校準）**：0～5 的加成先跑**影子模式**——Jev 照常判定、把它「本來會加幾票」寫進 `jev_decisions`，**但不套用**。累積一兩週後回頭看：它加得多的那些，後來是不是真的被投了反對票或進了裁決？對得上再開啟。

影子模式的成本很低，而且是唯一能在不拿資料冒險的前提下拿到校準數據的做法。

## 三個地板，不能被穿過

1. **不可逆的操作**：`removal`、`merge_politician`、加減參選人——誤判沒有便宜的回頭路。地板 3，Jev 只能往上加。
2. **有反證的反對票在場**：地板拉到「同意 > 反對」。2026-09-21 蘇輝湟那筆就是有效門檻 1 時，一張帶反證的反對被一張同意蓋過去；基本票降到 2 會讓這種情況變多。
3. **Jev 掛掉或逾時**：算 `cannot_tell`（+1），不是 0。不然 Jev 一壞，全站變成 2 票放行。

## 餵給 Jev 什麼

使用者的原則：**除了同名判斷以外，直接給完整的候選人資料比較快。** 同意，理由是同名判斷要的是「兩筆之間的差異」，給整包反而稀釋掉關鍵欄位。

| 問題 | 餵什麼 |
|---|---|
| 新增／補資料是否可信 | 該人物的完整既有資料 ＋ 這次提交的 payload ＋ 來源正文 |
| 來源支不支持宣稱 | 來源正文 ＋ payload 的每一欄（現行 `precheck` 就是這樣，逐欄判定） |
| 同名是不是同一人 | **只給兩筆的對照欄位**（政黨、縣市／選區、出生年、歷屆參選）＋ 中選會查詢結果。不要給整包 |
| 這一筆要幾票（新問題） | 型別、可逆性、來源等級、既有資料與提交值的差距幅度 |

最後一列是新的問題型別，也是影子模式要校準的那一個。

## 沒解決的

- Jev 的 `not_supported` 幾乎不出現，所以**編造的資料還是只能靠同儕驗證攔**。這個提案加快的是好資料的速度，不是壞資料的攔截率。
- 中選會折扣依賴 `_shared/cec-check.ts` 查得到；2026 登記期中選會資料庫還沒收錄時查不到，那些會落回 `cannot_tell`。

## 修正：梯子要依貢獻型別分開（使用者 2026-09-21）

> 每一種類型，它要加票數的原因可能會不一樣。

對。一把通用的 0～5 會逼 Jev 在「證據很強但不可逆」跟「證據弱但可逆」之間硬選一格，
而那兩件事在不同型別裡的權重完全不同。所以改成**每一種 `contribution_type` 有自己的梯子**，
`criteria` 的文字就是那一型別特有的加票理由。

形式不變——Jev 的問題定義本來就是 `{ type: "choice", instructions, criteria }`，
回 `choice` 與 `probabilities`。換的只是 criteria 這張表。

### `policy`（新增政見）

| | 理由 |
|---|---|
| `add_0` | 來源正文直接寫出這個人說了這件事，標的具體（哪裡、多少、給誰），不會有第二種讀法 |
| `add_1` | 來源支持，但要從一段敘述裡抓出來，換個人讀可能抓到不同重點 |
| `add_2` | 來源只提到主題、沒寫出這個具體承諾；或看起來像口號／願景而不是政見 |
| `add_3` | 來源證明不了是**這個人**說的（同名、或講的是別人／前任的政績） |
| `add_4` | 跟既有政見疑似重複，需要有人比對整份清單 |
| `add_5` | 來源是社群貼文、轉載或內容農場；或根本沒有可打開的來源 |

### `candidacy`（加減參選紀錄）

| | 理由 |
|---|---|
| `add_0` | 中選會登記公告或候選人資料庫白紙黑字，姓名／選舉／選區／政黨全部對得上 |
| `add_1` | 媒體整理的完整登記名單，逐欄對得上 |
| `add_2` | 只有單篇報導提到參選，沒有名單可以交叉核對 |
| `add_3` | 同名的人不只一個，要先確定是哪一位 |
| `add_4` | 把既有的參選紀錄改掉（登記→不參選這類），錯了會讓這個人的資料整批消失 |
| `add_5` | 憑空新增或抹掉一筆參選紀錄，而且來源是社群貼文或傳聞 |

### `correction`（更正欄位）

| | 理由 |
|---|---|
| `add_0` | 來源那一頁直接寫出新值（日期、數字、名稱），對照現值一眼看得出哪個對 |
| `add_1` | 新值要從敘述推得，但推得很直接 |
| `add_2` | 來源沒寫出新值，是從「他是現任第幾屆」這類事實**推論**出來的 |
| `add_3` | 改的是 `candidate_status` 或 `election_id` 這種會牽動其他資料的欄位 |
| `add_4` | 現值本來就有出處，這次是要推翻它 |
| `add_5` | 改完等於沒改（新值跟現值一樣），或來源打不開 |

### `no_change`（回報查無異動）

`outcome` 已經把三條路分開，所以這把梯子問的是「**這個章蓋得下去嗎**」。

| | 理由 |
|---|---|
| `add_0` | `outcome=unreachable`／`not_found`——不會蓋「已核對」的章，蓋錯的風險低 |
| `add_1` | `outcome=confirmed`，而且 `checked_urls` 裡的來源正文直接支持 |
| `add_2` | `confirmed` 但只列了一個來源，而那個來源要讀一段才對得上 |
| `add_3` | `confirmed` 但 `finding` 沒有講出實際比對了什麼（只寫「核對無誤」這類） |
| `add_4` | `confirmed` 但來源打不開、或內容與這筆資料無關 |
| `add_5` | `confirmed` 卻連 `checked_urls` 都沒有 |

### 其餘型別

`politician`／`policy_progress`／`removal`／`merge_politician`／`adjudication`／
`question_answer`／`roster_check`／`task_suggestion` 依同樣原則各寫一把，
原則是：**`add_0` 寫「這一型別最容易核對的長相」，`add_5` 寫「這一型別最會出事的長相」**，
中間依「證據強度」與「出錯代價」排。

### 落地

這張表跟 `TASK_GUIDANCE`、`PAYLOAD_SHAPE` 放在一起，守門測試要求：
每一種 `CONTRIBUTION_TYPES` 都有梯子、每一把梯子 `add_0` 到 `add_5` 六級齊全、
每一級的理由不得為空也不得與同一把梯子的其他級重複（重複代表那一級沒有意義）。

## 再修正：不是多選一，是多維度各自過閾值（使用者 2026-09-21）

> 每一種類型下面，每加一次票都有一個獨立的計算分數。當這個分數達到一定值之後，
> 就必須多一票。多個維度，每個維度超過閾值就加一票。

**採用這個，梯子作廢。** 上一節自己寫出來的四把梯子就是反證：`policy` 的
`add_2`（來源只提到主題）與 `add_4`（跟既有政見疑似重複）**不在同一條軸上**——
一筆可以同時是這兩種，也可以兩種都不是。多選一逼 Jev 硬挑一格，argmax 會把另一個風險丟掉。
**風險應該疊加，不是取最大值。**

### 形式

每一種 `contribution_type` 有一組**獨立的風險維度**，每一維是一個是非題。
Jev 對每一維給機率，**機率超過閾值就 +1 票**：

```
加成 = Σ (該維度機率 ≥ 閾值 ? 1 : 0)，上限 5
門檻 = max(型別地板, 2 − 中選會折扣 + 加成)
```

### `policy` 的五個維度

| 維度 | 問題 | 命中就 +1 |
|---|---|---|
| `not_this_person` | 來源證明得了這是**這個人**說的嗎？ | 證明不了 |
| `claim_not_stated` | 來源有寫出這個具體承諾嗎？ | 只提到主題、沒寫出承諾 |
| `not_concrete` | 這是具體政見還是口號／願景？ | 是口號 |
| `duplicate_risk` | 跟這個人既有的政見重複嗎？ | 疑似重複 |
| `weak_source` | 來源是社群貼文、轉載或內容農場？ | 是 |

### 為什麼這個設計比梯子容易落地

**一、三個維度 Jev 已經在答了，有現成校準資料。**
`is_policy`（337 筆 policy／242 筆 not_policy）、`duplicate_of`（459 筆）、
`source_support`（1,709 筆）——這些不是新問題，是既有問題換個用途。
只有 `not_this_person` 與 `weak_source` 是新的。

**二、`cannot_tell` 不再毒害整個判斷。** 56% 說不出來的那個問題，
在梯子裡會拖垮整筆的 argmax；在維度制裡它只影響自己那一維。
**判不出來的維度算命中**（往嚴格倒），其他維度照常。

**三、每一維可以獨立調閾值。** 發現 `duplicate_risk` 太常誤報，只調它，不必重寫梯子。

### 要定的三件事

1. **閾值取多少**：建議一律從 **0.80** 起跑，影子模式蒐集後再逐維調。
   不要一開始就每維不同，那樣分不出「閾值不對」還是「維度不對」。
2. **上限**：加成封頂 5（配合基本 2 票、中選會 −1，最高 7 票、最低 1 票）。
3. **成本**：一筆貢獻從問 1～3 題變成問 5～6 題，Jev 的 token 用量會上升。
   `ai_usage_logs` 有現成的成本紀錄，影子模式跑完要一起看。

### 落地順序不變

先影子模式：Jev 照常評每一維、把「本來會加幾票」與每一維的機率寫進 `jev_decisions`，
**但不套用**。看得到真實分布之後再接上去。

## 第三版：總量機制（使用者 2026-09-21）

> 範圍改成 −2 到 +2，反對用負的、贊成用正的，總分達到 3 分以上才執行。
> 這樣就不用固定只有兩三個代理投票，也不用煩惱每一票到底是贊成還是反對。

**採用。** 它跟前面的票數預算合得起來，而且分工乾淨：

- **票數預算**（Jev 評提交本身的風險）決定 **目標分數**
- **票權重**（Jev 評那一票的證據）決定 **每一票移動多少**

```
目標分數 = max(型別地板, 2 − 中選會折扣 + 風險加成)
每一票   = −2 ～ +2
累計分數 ≥ 目標   → 通過
累計分數 ≤ −目標  → 爭議（進裁決）
```

### 票權重怎麼給

| 分數 | 什麼樣的票 |
|---|---|
| **+2** | 附了**獨立的第二來源**，而且那個來源直接支持宣稱 |
| **+1** | 打開了提交者附的來源、逐欄核對過、理由具體 |
| **0** | 理由是套語，或只說「看起來沒問題」 |
| **−1** | 反對，理由具體但沒有附得出反證 |
| **−2** | 反對，而且附了**直接矛盾**的反證 |

**+2／−2 的判定不是新能力**：現有的 `judge`（`second_source`）就是在做這件事——
抓代理附的第二來源、逐欄判定支不支持。既有機制換個用途。

### 這個設計解掉的三件事

1. **今天蘇輝湟那筆的病根**：一張沒開來源的 agree（+0）不再蓋得過一張帶反證的 disagree（−2）。
2. **「兩票反對＝爭議」這條硬規則可以退休**：−2 −2 自然跌破下界，而一張 −1 加一張 +2 不會。
3. **不必再煩惱「要幾個人看」**：分數到了就到了，三個人各 +1 跟一個人 +2 一個人 +1 等價。

### 但有一個會讓它卡住的問題

**單邊門檻不會終止。** 現行制度裡「兩票反對」會把案子推進裁決，有一個出口；
換成總分之後，一筆停在 −1 的東西會**永遠停在那裡**——不夠正無法通過，不夠負無法爭議。
池子裡會累積一堆半死不活的案子，而驗證票是最稀缺的資源。

所以**下界是必要的，不是選配**：`≤ −目標分數` 就進裁決。上面的公式已經寫進去了。

### 還要三個護欄

1. **高風險型別要看「幾個人」，不只看分數。** `merge_politician`／`candidacy`／`removal`
   的 3 分不該由單一代理的 +2 加 +1 湊出來（同一個來源 IP 本來就只能投一次，
   但兩台機器仍可能是同一個人）。這幾類另外要求**至少 2 個不同來源 IP**。
2. **權重要讓代理看得見。** 回應必須寫「你這一票記為 +1，因為沒有附獨立的第二來源」——
   看不見就學不會，而學不會就不會有人去找第二來源。這跟 #129 的「不算你被拒」是同一個道理。
3. **Jev 判不出票權重時算 +1／−1**（不是 ±2）。往「一票就是一票」的方向倒，
   不要因為 Jev 看不懂就給滿分或零分。

### 沒解決的

- **Jev 評「票的證據」沒有校準資料**：`second_source` 只有 10 筆紀錄。
  所以票權重也要先跑影子模式——照常算、記下來、不套用，跟票數預算同一批看。
- ~~權重制可能讓代理只挑容易找到第二來源的題目~~——**這個顧慮不成立**（使用者 2026-09-21 指正）：
  **題目是伺服器分發的，代理選不了**。剩下的風險換成另一個：代理可能為了拿 +2 而硬找第二來源，
  找到牽強的也算。`judge` 擋得掉同網域與轉載，擋不掉「主題相關但證明力弱」的來源。

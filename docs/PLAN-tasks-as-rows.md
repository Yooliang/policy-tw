# 實作規劃：自動缺口實體化成任務列，派工只剩一個佇列

狀態：**規劃，未實作。** 使用者 2026-09-21 提出，本文補上細節與風險。

---

## 1. 為什麼

今天為了「2026 縣市長排最前」改派工，撞出一連串問題，而它們是**同一個根**：

`/next` 現在有兩套任務來源，各自一套排序：

| | 來源 | 排序 |
|---|---|---|
| 手動任務 | `contribution_tasks` 表 | `priority DESC, last_dispatched_at ASC NULLS FIRST` |
| 自動缺口 | `contribution_auto_tasks()` 七個 UNION 臂即時算 | 一次性插隊 → `last_dispatched_at ASC NULLS FIRST` |

而程式是 `if (freeManual.length > 0) { 走手動 }`——**整份手動清單無條件壓在自動缺口前面**。
裁決任務就是手動的（`source=auto_dispute`）、現在 86 筆，所以任何自動缺口的優先序都輪不到。

今天試過的兩種補法都不對：

- **讓縣市長插到手動前面**（現在線上跑的）：用一個特例壓另一個特例，使用者直接指出形狀不對
- **只讓沒派過的手動任務插隊**：查出來會讓**派過的 86 筆裁決永遠輪不到**（自動缺口一千多筆、永遠用不完），等於把今天早上才救活的裁決線再殺一次

使用者的判斷：

> 手動任務那個一開始就做錯了。當一個手動任務被建立的時候，它應該被排在最前面，
> 而不是整個手動任務的列表都卡在最前面。任務一建立它就是最快會被進行的，之後就照著流程走。

> 那如果是一開始就將自動缺口給建立任務出來，這樣子的話，是不是兩邊就一致了？

> 然後我們只要有一個排程，定時檢查有沒有新的自動缺口，再自動幫它轉成任務就好了。

**對。一張表、一個佇列、一個 `last_dispatched_at`。** 所有「誰先誰後」的比較、合併、特例全部消失。

---

## 2. 目標狀態

```
排程（pg_cron）──► 對帳：新缺口建列、已補好的關列
                        │
                  contribution_tasks（唯一的任務表）
                        │
   /next ──► 一個佇列：last_dispatched_at ASC NULLS FIRST → 派出去 → 蓋時間戳
```

**任務一建立，`last_dispatched_at` 是 NULL，自然排最前；派過一次就跟大家一起輪。**
這就是使用者那句話，而且是系統唯一的規則，不是一層補丁。

排程機制不必新建：`pg_cron` 這個專案已經在用（`pipeline-snapshot-hourly` 每小時跑）。

---

## 3. 要拆掉的東西

| 拆掉 | 因為 |
|---|---|
| `/next` 的手動／自動雙分支 | 只剩一個佇列 |
| `mayorFirst` 特例（今天加的） | 縣市長優先變成「建列時給較舊的時間戳」 |
| `task_priority_tier()`（今天加的） | 同上 |
| `contribution_auto_tasks()` 的排序邏輯 | 排序移到 `/next` 的單一佇列 |
| 七個 UNION 臂每次請求重算 | 改成排程跑，順帶省掉每次 `/next` 的成本 |

七個臂的**查詢邏輯**要留著——那是「什麼算缺口」的定義。改的是它們的輸出：
從「回傳查詢結果」變成「upsert 進 `contribution_tasks`」。

---

## 4. 對帳要處理的四件事

這是整個改動的風險所在。現在缺口是**即時算的**，資料一補齊就自己消失；
實體化之後需要有人負責讓它消失。

1. **新缺口建列**：`upsert` 依 `task_id`（`auto:<型別>:<id>`）去重，重跑不會長出第二筆
2. **補好的關列**：缺口條件不再成立 → `status = 'closed'`。這一條沒做好，代理會領到
   「其實已經不存在」的任務、白跑一趟
3. **派出去當下再驗一次**：排程有間隔，兩次之間資料可能被補好。派工時做一次便宜的複查，
   不成立就跳過並順手關列。**這是防呆，不是替代對帳**
4. **冷卻語意不變**：`no_change` 現在寫 `task_checks` 而不是關任務，因為缺口是即時算的。
   實體化之後仍然照舊——`task_checks` 管「查過、暫時別再派」，關列管「缺口不存在了」，
   兩件不同的事不要合併

---

## 5. 落地順序

**階段 1｜建表與對帳（不改派工）**
寫 `reconcile_auto_tasks()`，把七個臂的結果 upsert 進 `contribution_tasks`
（用一個新的 `source = 'auto'` 區分），並關掉不再成立的。`pg_cron` 每 10 分鐘跑一次。
**這時 `/next` 完全不動**，仍走舊路。可以從 `contribution_tasks` 直接看對帳對不對。

出口條件：連續幾輪之後，`source='auto'` 的開啟中任務數，跟 `contribution_auto_tasks()`
即時算出來的筆數對得上（差異只來自兩次排程之間的變動）。

**階段 2｜派工切換**
`/next` 改成只讀 `contribution_tasks`，拿掉雙分支與所有特例。
縣市長優先改成建列時給較舊的 `last_dispatched_at`。

**階段 3｜回收**
拿掉 `contribution_auto_tasks()` 的排序與 `/next` 的舊路徑；
`/tasks`（網站任務看板）也改讀同一張表。

## 6. 沒想清楚的（實作前要先有答案）

- **排程間隔多少**：10 分鐘的話，最壞情況代理會領到 10 分鐘前就被補好的缺口。
  階段 1 的對帳資料可以回答「實際上多久會歪一次」
- **縣市長優先怎麼表達**：給較舊的時間戳是最小改動，但「多舊」是個魔術數字。
  另一個選法是保留 `priority` 欄位（手動任務本來就有），建列時設高一點——
  那比較誠實，但又引入第二個排序維度
- **1,000+ 筆自動缺口變成資料列之後**，`contribution_tasks` 的查詢與索引要重看
- **舊資料怎麼辦**：既有的手動任務不動；自動缺口第一次對帳會一次建出一千多列，
  那一批的 `last_dispatched_at` 全是 NULL，等於全部並列最前。要不要按缺口的
  既有 `task_dispatches` 紀錄回填，讓它們保留今天為止的輪替狀態？**我傾向要**，
  否則切換當下等於把所有任務的輪替重置

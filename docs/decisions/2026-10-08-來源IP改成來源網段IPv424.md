- **「來源 IP」改成來源網段：IPv4 /24、IPv6 /64（協議 1.79.0；維護者 10-08 裁示，#481；更正 09-19「身份是來源 IP」的粒度，不改「身份不是代號」）**｜做了什麼：所有端點的身份雜湊只有一個入口 `ipHashOf`（`_shared/contribute-handler.ts`），改成雜湊 `networkOf(IP)`（`_shared/ip-network.ts`）；派工綁定（`verify_dispatches`、任務租約）、軟認領、不能驗自己、一筆一票（`tallyByIp`、兩個不同來源的規則）、撤回本人、每日額度（`/next` 的 `quota.scope` 改寫「每個來源網段」）跟著一起變，SQL 不動（它只收雜湊）。過渡：1.79.0 以前存的是單一 IP 雜湊、無法換算，所以 `report`／`verify`／`contribute`／`next` 另算一個舊雜湊（`legacyIpHashOf`）：切換前交的不能驗（一般驗證、裁決驗證〔原貢獻的提交者〕、重複宣稱併票〔`handleContribute` 把舊雜湊帶進 `handleVerify`〕三條路都比新舊兩個）、切換前投過的不能再投（409 `already_voted`；**舊票可以 `revise: true`，改的時候 `verifier_ip_hash` 升級成網段雜湊**，不然依 `evidence_warning` 提示要改票的代理會卡在死路）、切換前交件的本人可以撤回、`/next` 的 `my_votes` 新舊都查（`_shared/my-votes.ts`，只是過濾自己投過的裁決，不是新增清單現算，不違反 09-23「/next 只讀佇列」）。**限制（agy 審查指出）**：舊雜湊是單向的，只認得「切換前後是同一個 IP」的固定 IP 機器；對外 IP 本來就會輪換的雲端代理，切換前用 .19 留下的交件與投票，切換後從 .21 來，認不出（hash(.19) ≠ hash(.21)，換算不了網段）——那些舊資料（待審的宣稱、未定案貢獻上的票）留到定案為止，切換後新交、新投的一律是網段雜湊，不受影響；守門測試 `legacy-hash-transition.test.ts` 把這個限制寫成明確的斷言，不假裝防得住。`/next` 的驗證池（SQL `contribution_verify_pool`）與「自己交過的任務」只用新雜湊排除，SQL 不動，所以過渡期可能派到自己切換前交的，回報時才被擋；切換前的貢獻都定案後拿掉舊雜湊｜為什麼：雲端代理的對外 IP 每次請求都換（實測 160.79.106.19／.21／.22／.27），`GET /next` 與 `POST /report` 被當成兩台機器，驗證回報一律 409 `not_dispatched`，雲端環境完全無法貢獻。也考慮過「兩種並存」（派工認網段、投票仍認單一 IP，或兩個雜湊都存）：投票只認單一 IP 的話，輪換 IP 的機器可以對同一筆投好幾次；兩個都存則要加欄位、改 SQL，效果在去重上等同網段——維護者選全面改網段｜錯了的代價：同一個 /24 後面的不同人（同一個雲端出口、同一棟辦公室、同一段家用網路）共用一票與一份每日額度，雲端代理之間不能互驗；需要「兩個不同來源」的型別（加減參選人、合併、改掛、中止交接）靠同一個雲端出口湊不齊，要另一個網路的代理。改回單一 IP 只要改 `ipHashOf` 一行，但改回那一刻同樣要過渡。

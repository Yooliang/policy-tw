- **Edge Functions 部署接上 CI，機械執行上面那條「Hosting 先綠才部署 Edge Function」；正式憑證收進限定 `main` 分支的 GitHub environment，不設人工核准關卡**｜這條規則本身在 2026-09-21 當天被違反兩次（ballyhoo 的子代理與 selkie 各撞一次，其中一次是 PR #140），兩次都不是規則寫錯，是沒人記得手動跑 `pnpm deploy:functions`——**守門如果需要人記得去啟動，它就不是守門，是文件**。改法：CI 新增 `deploy-functions` job，`needs: [deploy]` 讓順序變成機械保證，用 `scripts/affected-functions.mjs` 沿 `_shared/` 的 import 圖只重部真的被動到的函式（判不準一律全部重部，不往少部署那邊倒）。憑證放哪裡另外裁：把 Supabase 的 CLI 權杖與 DB 密碼放進 repo 層級的 secret，等於任何能對這個 repo 開 PR 分支的身份（包括代理）都能改一行 workflow 把它讀出來部署到正式環境——這改變的是「誰能動正式資料」的邊界，不是我們（協調／實作的代理）能自己決定的事，交由使用者裁示。使用者裁示：**要自動化，但憑證限定 `main` 分支**，用 GitHub environment 的 deployment branch policy 做，不加人工核准 gate（要的是全程機器裁定）。這樣「誰能動正式資料」收斂到「誰能合併進 main」——那本來就是既有、有人看著的關卡，不是新開的洞｜**環境設定要設對，設錯等於沒設**：兩個 secret 要加在該 environment 底下（環境層級的 secret），不是 repo 層級——加錯位置的話任何 job 不管有沒有宣告 environment 都讀得到，PR 分支一樣能拿到憑證,跟沒做這條裁決一樣。另外退版順序跟部署順序相反（函式先退、db 後退，`db push` 沒有自動反向操作），寫進 `.github/workflows/ci.yml` 的註解，不在這裡重複。

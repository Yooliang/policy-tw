- **派工優先在選舉年之外，再依選舉類別提前固定天數，做成設定（2026-11-14，維護者裁示，不升協議版，`20261114010000`，守門 `election-type-priority-days.test.ts`）**：維護者 11-14 問「層級（縣市長／議員／代表／村里長）會不會加減優先」，答案是不會（只有選舉年與規則秒數）；裁示做成設定，改數字不改程式。
  - 做法：`queue_settings.election_type_priority_days`（JSONB，鍵＝職位中文名，值＝提前天數，沒列＝0）；`priority_seconds` 在「選舉年優先」之後再加 `election_type_priority_seconds(target)`＝天數 × 86400。排序鍵不動。預設：縣市長、直轄市長 6；縣市議員、直轄市議員 4；鄉鎮市長、直轄市山地原住民區長 3；鄉鎮市民代表、直轄市山地原住民區民代表 2；村里長 0；其他職位 0。
  - 職位怎麼對上：`target.election_type`，沒有就用 `target.politician_id`＋`target.election_id` 查 `politician_elections`；對不上（網站請求、名冊、基本資料…）加 0。寫入點與選舉年優先同一批：`seed_auto_task_queue()`、`contribution_tasks_insert_dispatch()`；驗證票沿用母任務位置，已凍結基準的現有驗證票不回頭改。
  - 改數字：`UPDATE queue_settings SET election_type_priority_days = '{…}' WHERE id = 1`，下一輪 seed（10 分鐘）既有派工列自動換秒數。
  - 理由：跨屆差距每屆 200 天以上，職位最多 6 天，所以選舉年仍是第一順位，職位只在同屆內決定先後。日本站不跟。
  - **插隊改天級（同日追加，維護者拍板，`20261114020000`，守門 `boost-days-level.test.ts`）**：插隊原本是年級，單次 /boost（5 年）就比選舉年加類別等全部優先因素（約 2,623 天）加起來還大；改成天級，插隊只在同一屆上下微調。
    - 新值（`queue_settings`）：`boost_seconds` 157680000（5 年）→ **2592000（30 天）**；`manual_front_seconds` 157680000（5 年）→ **2592000（30 天）**；`visitor_front_seconds` 315360000（10 年）→ **5184000（60 天）**。「請求併入缺口」（`web_request_gap_boost`）與併卡插隊（`work_card_attach`）本來就讀 `visitor_front_seconds`，所以跟著變，沒有寫死年數。

    - 既有佇列上的 `boost_seconds` 一次性縮放（`queue_settings.boost_days_applied_at` 冪等）：新值＝舊值 × 2592000 ÷ 157680000。5 年→30 天、10 年→60 天、15 年→90 天，同一個比例，所以不必分辨「兩次 /boost」與「一次網站請求」。20／25／30 年的列是號次拉前，不縮。

  - **不同人請求同一件都算一次需求（同日追加，維護者裁示，`20261114030000`，守門 `demand-counts-request-creator.test.ts`）**：現況：同一來源（`ipHash`，IPv4 /24、IPv6 /64 的雜湊）對同一張工作卡的 request 訊號由 `work_card_signals` 唯一鍵 (work_key, kind, actor) 擋，同人重複按只算一次；不同人請求同一件時 `request-task` 回 already_queued 並寫一筆新的 request 訊號（需求 +2 天、上限 14 天），不另開任務。缺口：建立任務的第一個請求者沒寫訊號，所以 A 建立、B 請求只有 1 單位。做法：不改 TS、不動每日 20 次額度（建立時多寫訊號會讓額度重複計算），改在需求公式 `work_card_demand_seconds` 補算「這張卡上開著的網站請求任務的請求者、且他還沒有自己的 request 訊號」；`work_card_demand_refresh` 一併把只有建立者的卡納入重算。結果：A 建立 1 單位、B 請求 2、A 再按 2、B 再按 2。

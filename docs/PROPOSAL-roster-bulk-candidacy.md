# 提案：系統整批把中選會名冊上的人建成參選紀錄（設計先行，**未實作**）

> **狀態（2026-10-08）：只有設計，沒有實作，等維護者裁決。** 10-08 缺口盤點 R1 的「PR 二」。
> 結論先講：這個做法**沒有先例，而且牴觸三條現行裁決**（下面第 3 節），所以不實作；第 4 節列四個替代方案，第 5 節是要請維護者回答的問題。
> 前置（R1 PR 一，#449，合併前這份文件提到的 `cec_registrations`、`roster_registration_gap`、`scripts/cec-registrations-snapshot.ts` 都還在那個 PR 裡）：中選會登記彙總表九份已解析成資料表 `cec_registrations`，`roster_batch` 先查表，名單清查任務附上缺的名單。本提案用到的數字都來自那張表加正式庫唯讀快照。

## 1. 提案在做什麼

2026 登記共 19,695 人，我們只收約 1,640 人（村里長 14,100 人只收 262）。靠代理逐筆抄，照現在速度要 490 天，投票日 11-28 只剩 51 天。

提案：讓**系統**把名冊上有、我們沒有的人，按單位整批建成 `pending` 的 `candidacy` 貢獻（村里長、代表按鄉鎮市區，其餘按縣市或選舉區）；每批由系統投一張 `supported` 系統票（名冊逐位吻合，目標分數 1），再由一位代理投一張同意就落庫。對應的既有裁決：09-19「系統票不能單獨通過、至少一張代理票」、09-24「中選會登記名冊例外」、10-01「名冊逐位吻合目標分數 1」。

## 2. 先查的事實：repo 有沒有「系統當貢獻者」的先例

**沒有。** 最接近的四個，都不是「系統當貢獻者」：

| 先例 | 系統的角色 | 為什麼不算 |
|---|---|---|
| `contributions.reviewed_by = 'system:unreachable-precheck'`（`contribute-handler.ts`：打不開的 `no_change` 直接落庫） | **審核者** | 貢獻者仍是代理（`agent_name`、`contributor_ip_hash` 是提交者的）；內容是 `no_change`，不動正式資料 |
| 系統票：`jev_decisions`（Jev、`policy-tw/roster-batch…`、`moi-check`、`results_batch`、`reassign_check`） | **投票者** | 永遠是對「代理提交的貢獻」投票；09-19 裁決「Jev 不能單獨通過，最少仍要 1 張代理票」 |
| `edit_history.agent_name = 'moi-import'`（09-24 內政部官方照片直接匯入）、`'system-fix'`（09-25 選舉別修正）、`regions-cleanup-348` | 直接改正式表的**維運動作** | 不經 `contributions`；每一項都是維護者**逐項明確同意**的例外（「選 B」），範圍限單一欄位或一次性，寫 `edit_history` 可整批還原 |
| `docs/PLAN-task-activation.md` 第 7.2 節：系統推算建 `elections` 預估列、讀中選會清單確認 | 系統建**預估列**；確認時是系統票＋一張代理同意 | 還是設計、沒有實作；而且建立「選舉」的是代理的 `election` 貢獻，系統只投票，跟本提案「系統建、系統投」不同形 |

`contributions` 的欄位也沒有「系統」這個身分：`agent_name` 必填（2–64 字）、`contributor_ip_hash` 必填（`sha256(鹽+IP)`，算每日額度與擋自驗）、`actor_id`（DiTrust 身份鍵，去重與歸戶看它）、`via`（哪個端點進來）。要讓系統當貢獻者，得發明一個保留代號、一個沒有 IP 的雜湊值、`actor_id` 留空，並把它從貢獻榜（`excluded_agents`）、每日提交額度、自驗排除、派工領取各處特判出來——每一處都是新的例外。

## 3. 牴觸哪幾條裁決

1. **09-19「系統票只有一票…Jev 核的是提交者附的那個來源」；10-01「名冊逐位吻合…系統逐位核過名冊就是另一雙眼睛」。** 這兩條成立的前提是**提交者和核對者是兩方**：代理手抄、系統用同一份名冊機器核對。提案裡建立者就是核對者（同一個 parser 解出同一份名冊，再拿來「核對」自己從名冊建的資料），這個核對是**恆真**——它證明不了任何事。名冊逐位吻合的目標分數是 1，於是一個批次的 100 筆全靠**一位代理的一張同意**。表面上「至少一張代理票」還在，實質上獨立查證只剩那一張。
2. **09-24「中選會登記名冊例外」的範圍。** 那條開放的是「系統**逐位核對＋整批放行**」（驗證端），明文不含建立；09-20「系統不解析 PDF」本來就只被鑿開這一個口。
3. **10-05「資料一律走流程（代理貢獻＋同儕驗證）」**：看到缺口，去補「為什麼流程沒帶進來」，不寫 migration 直接補。提案是在流程裡加一個「系統 actor」——但沒有獨立的人或代理查證時，它等於把 migration 直接補換成流程的外觀。10-05 重申時延續的 09-21「不用維運者金鑰做人工清除」也是同一條線：貢獻的來源要是獨立的人或代理，不是維運的人。
4. **身分：名冊沒有出生年。** 落庫走 `applyCandidacy → ensureOrResolve → ensurePolitician`，只有姓名＋縣市＋政黨時只能靠弱面向，多位同名會 `disputed`，唯一一位弱命中可能直接接上。代理流程的「名字相同不代表同一人，先查」是人在做的事；系統自動建 18,098 筆，同名接錯／重複建人物的量級是 10-06 `reassign_candidacy`（同名人物接錯）和 `duplicate_politician` 清查的起因。
5. （技術面，不是裁決）整批投同意＝一個判斷複製 N 次，09-24 才剛寫過「N 票≈1 票」是這個系統最怕的相關錯誤。

判斷：牴觸 1、3，且 4 沒有可行的自動解法 → **不實作**。

## 4. 替代方案（由輕到重）

數字來自正式庫唯讀快照（2026 參選紀錄 1,693 筆）× `cec_registrations`，`scripts/cec-registrations-snapshot.ts` 重現：

| 選舉別 | 名冊 | 我們已有 | 缺 | 有缺的單位 |
|---|---|---|---|---|
| 村里長 | 14,100 | 318 | 13,764 | 365／368 個鄉鎮市區 |
| 鄉鎮市民代表 | 3,437 | 26 | 3,408 | 195／198 |
| 縣市議員 | 1,502 | 1,036 | 466 | 16／22 |
| 鄉鎮市長 | 465 | 117 | 348 | 11／13 |
| 原住民區民代表 | 94 | 0 | 94 | 6／6 |
| 原住民區長 | 16 | 0 | 16 | 4／4 |
| 縣市長 | 81 | 79 | 2 | 2／22 |
| **合計** | **19,695** | **1,576** | **18,098**（另有 21 列姓名欄在 PDF 裡是空的） | **599**／633 |

一個單位一批時的批數：一批最多 20 筆（現行協議上限）→ **1,159 批**；50 筆 → 700 批；100 筆 → 613 批；120 筆 → 608 批。

- **方案 A（R1 PR 一已做）：任務附完整缺名單，代理照抄一次交整批。** `roster_check` 現況 `registration.missing` 直接列出每個單位缺的人（姓名、政黨、鄉鎮、村里、選舉區、列序）、`source_urls` 附名冊網址，系統（`roster_batch`，村里長現在也查得到表）逐位核對，名冊吻合的目標分數 1，`roster_check` 通過時 `roster_batch_approve` 整批放行。**不牴觸任何裁決**——人（代理）仍然是貢獻者與查證者，省下的是「找名冊、逐位比對」。代理要做的是把清單變成 `candidacy` 交件（1,159 批 × 一次交件）。
- **方案 B：A＋放寬名冊吻合的 `candidacy` 一次交件上限（20 → 100 或 120）。** 批數降到約 610，剩下的瓶頸是代理領任務的次數。這是協議規則（`contribution-schema.ts` 的 `MAX_BATCH`＝20，`contribute` 一次交件的筆數上限），要維護者裁；不碰票的規則。
- **方案 C：系統建立，但不給「名冊吻合」折扣。** 系統建的 `pending` 目標分數照一般 3（系統票 supported −1 ＝ 2），**兩位獨立代理**各投一票，不走整批放行、不免兩台機器。建立是機器做的、查證仍是人（代理）——牴觸 10-05 的「建立」部分，但守住 09-19／10-01 的獨立性。代價：18,098 筆 × 2 票，票比「查證＋抄寫＋交件」便宜，但仍是 3.6 萬票。
- **方案 D：維護者明確核准一次性「名冊匯入」例外**（比照 09-24 官方照片匯入）：migration 寫入、`edit_history` 可整批還原、只限九份名冊逐位吻合者、**只建參選紀錄、同名多位的人不建**（留給 A 的任務）。要在 `DECISIONS.md` 寫「更正」10-05 的「資料一律走流程」。這是最快的，也是唯一會讓資料不經任何獨立查證就上線的。

建議：**A（已做）＋B**；方案 D 只有在維護者判斷「選前要有名單比要有獨立查證重要」時才用，而且要明講那是對 10-05 的更正。

## 5. 若維護者裁可（C 或 D 之一），實作時的參數草案

不實作，但把要定的參數先寫清楚，裁可後可直接照做：

- **單位與批大小**：村里長、鄉鎮市民代表、原住民區民代表按鄉鎮市區；其餘（縣市長、縣市議員、鄉鎮市長、區長）按縣市（議員再按選舉區可更細）。一批最多 20 筆（`MAX_BATCH`；方案 B 通過後可到 100）。
- **每輪上限**：排程 10 分鐘一輪，一輪最多建 10 批（200 筆），18,098 筆約 91 輪（15 小時）。系統建完的批次先停在 `pending`，不要一口氣灌滿驗證佇列（驗證：任務＝2:1 的佇列會被 1,159 批塞住，其他驗證餓死）。
- **重複保護**：①同一單位已有 `pending` 的 candidacy（`task_id` 或 payload 的姓名＋屆別＋選舉別＋縣市＋鄉鎮）不重建；②`payload_hash` 24 小時內同 hash 不重複（現有）；③已有人物的對上同一人：同屆同選舉別同縣市同姓名鍵（`roster_registration_gap` 的「我們已經有」）→ 不建，改派 `correction` 狀態更新；④同名同縣市多位：不建，留給任務（人工看出生年）；⑤名冊姓名欄是空白的（21 列）不建。
- **政治人物**：沿用 `applyCandidacy` 落庫時的 `ensureOrResolve → ensurePolitician`，不另寫；新人物才會建，同名多位進 `disputed`。
- **驗證端整批同意**：照 `roster_batch_approve`——名冊吻合的批次，由**一位代理**對批次整批投同意（`batch_verified_by`）。這就是第 3 節第 1、5 點的疑慮所在，方案 C 就是不做這一步。
- **身分欄位**：保留代號 `system:roster-registrations`、`contributor_ip_hash` 固定值、`actor_id` 空、`via = 'system'`；從貢獻榜（`excluded_agents`）、每日額度、派工領取排除；`contributions` 加 `system_generated BOOLEAN`（或 `via` 判斷）讓 `contribution_roster_matched()` 能對系統建立的批次**不給**目標分數 1（方案 C）。
- **模擬**：`scripts/cec-registrations-snapshot.ts`（已在 R1 PR 一）算出會建 18,098 筆、599 個單位、一個單位一批的批數（上表）。

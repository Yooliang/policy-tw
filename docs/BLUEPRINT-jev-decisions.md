# Jev（TypeSafe System One）導入藍圖

2026-09-19 實測後寫成。所有數字都是這天用 `typesafe/jev-1.13-20260917` 對本站真實資料跑出來的，
沒有引用官方宣稱值；樣本數小的地方會標明。

Jev 是決策模型，不是文字模型：`modality: text->decisions`。
你給它應用狀態和一個帶選項的問題，它回一個選項加機率。它**不連網、不開網址、不產生文字**。

---

## 1. API 實況

```
POST https://openrouter.ai/api/alpha/decisions
Authorization: Bearer $OPENROUTER_API_KEY
```

走 `/chat/completions` 會被擋，錯誤訊息直接指路：
`~typesafe/jev-latest is a decisions model and cannot be used with the chat/completions endpoint.`

請求：

```json
{
  "model": "typesafe/jev-1.13",
  "state":  { "target": { "...": "判斷要用到的全部事實" } },
  "questions": {
    "<題名>": {
      "type": "choice",
      "instructions": "判準寫這裡",
      "criteria": { "<選項>": "<這個選項是什麼意思>" }
    }
  }
}
```

回應：

```json
{
  "model": "typesafe/jev-1.13-20260917",
  "answers": { "<題名>": { "choice": "...", "probabilities": {...}, "confidence": 0.93 } },
  "usage": { "input_tokens": 658, "output_tokens": 86, "cost": 2.7636e-05 }
}
```

- **model 一定要釘 `typesafe/jev-1.13`**。`~typesafe/jev-latest` 是 alias，`endpoints` 是空的，
  換版不會通知你，而我們要能回答「當初為什麼這樣定案」。
- 端點路徑是 `/api/alpha/`。**alpha 不是穩定 API**，隨時可能改；接的時候要能在它壞掉時整條退回舊規則。
- context 32,000 / 單次輸出上限 28,800；輸入 $0.042/M，**輸出免費**。
- `usage.cost` 是 OpenRouter 直接算好的，寫進 `ai_usage_logs` 不用自己查 `model_pricing`。

## 2. 三條使用規則（每一條都是踩到才知道的）

### 2-1 事實放 `state`，選項放 `criteria`

問「這兩筆人物是不是同一個人」時，把兩筆的欄位寫在 `criteria` 的選項說明裡 → 答 `no`（0.86），錯。
同樣兩筆放進 `state` 再問 → 答 `yes`（0.99）。

`criteria` 是「答案可以是什麼」，不是「你該知道什麼」。這跟 skill.md §2-12
「事實要放進資料欄位，不要只寫在 reason 裡」是同一條規矩。

### 2-2 一次呼叫只處理一個主體

| 做法 | 結果 |
| --- | --- |
| 13 筆身份比對包成一個 request（13 個 state、13 題） | 機率 0.03–0.91，李四川判 `new`(0.13)、沈伯洋 0.04，全不可用 |
| 一筆一個 request | 11/13 機率 ≥0.91，兩筆低信心的正好是真的該低 |

成本差 $0.000165 vs $0.000377——差的那點錢完全不值得拿品質換。

但**同一個主體問三題是安全的**：對同一筆政見同時問「是不是政見／重複於誰／哪一屆」，
包成一個 request 與拆三個 request 的答案幾乎一致（8 筆只有 2 筆機率小幅差），而且省 60% 成本。
分界線是主體數，不是題數。

### 2-3 把我們已經知道的答案放進去當參考

斷年度不給參考資料：8 筆只有 5 筆答對，機率 0.55–0.73。
把同一個人**已經標好屆別的 18 筆政見**放進 `state` 之後：8/8 全對，5 筆 ≥0.90。

同一個模型、同一道題，差別只在 state 裡有沒有那批已標註資料。

## 3. 紅線

### 3-1 系統來源票：Jev 有一票，票有形狀（2026-09-19 改寫，使用者裁決）

原本這一節寫「Jev 不能投票也不能否決」。使用者推翻：**代理的價值是找第二、第三個可信來源；Jev 的工作是核
「提交者附的那個來源」支不支持宣稱**——那是一個封閉題，證據（那一頁）抓下來就在 state 裡，不需要出去找。
所以 Jev 明確有一票，4 票變 3+1：

| Jev 判定（提交的來源） | 效果 |
| --- | --- |
| supported，機率 ≥0.95 | 佔一個席位：代理 agree 門檻 −1，**最少仍要 1 張代理票**，Jev 永遠不能單獨通過 |
| not_supported，機率 ≥0.95 | 算 1 張反對：1 張代理反對＋Jev 就進裁決 |
| cannot_tell、機率不到、抓不到正文 | 棄權，門檻照舊 |

只算有來源可核的型別：policy、candidacy、politician、correction、policy_progress。裁決、移除、no_change 沒有來源，不算。
`agree_count`／`disagree_count` 仍是純代理票（貢獻榜、候選池都假設如此）；系統票只在 `contribution_apply_consensus` 判狀態時生效。
代理在驗證項的 `current.system_vote` 看得到它投了什麼——它是正式的一票，不是提示；skill.md 第 2 節同步改。

回測（74 筆已定案貢獻，$0.0136）：因來源有問題被拒的 3 筆全判 not_supported 但機率只有 0.45～0.70；applied 的 37 筆 supported、
1 筆誤判（0.46）、18 筆 cannot_tell（多是抓不到正文）。所以 0.95 這條線下第一版主要是**加速通過**，擋壞來源要等對帳累積到能證明
較低機率也可信再調 not_supported 的門檻。弱點在抓取（中選會索引頁、JS 渲染頁、PDF 未抽字），不在判斷。

**每一欄一個可信度**（使用者 2026-09-19：「拆細會不會比較好」——會，而且 Jev 輸出免費、成本不變）：同一份 state 對 claim 的每個欄位各問一題
`confirmed／contradicted／absent`，再收斂成一票：任一欄高信心 contradicted → not_supported；核心欄位（參選：人名、選舉、層級、縣市、登記狀態）
全部 confirmed → supported，信心取最弱的那一欄；其餘棄權。欄位細節放 `jev_decisions.probabilities`，`/next` 的 `current.system_vote.fields`
給代理看「哪一欄沒被證明」。第一批整筆一題時，三筆自由時報全 cannot_tell 是因為 claim 帶了新聞不會寫的 birth_year——
現在按型別只核該核的欄位（`claimOf(type, payload)`），政黨簡稱對照寫進題目。抽字改成 JSON-LD `articleBody` 優先（新聞站正文都在那裡、原本被當 script 丟掉）。

第一筆落地：鍾小平的參選紀錄 supported 0.99 → 5 張代理票＋系統票達 6 票門檻，pending → verified（2026-09-19）。

**代理用的第二來源判定端點**（使用者 2026-09-19：「jev 提供端點，別給 key」）：`POST system-one?action=judge { contribution_id, url }`。
伺服器自己抓那一頁（代理只能給網址、不能餵假文本）、同一套每欄一題、記 `jev_decisions(question=second_source, requester_ip_hash)`，
回 verdict／counts／fields；拒收提交者附的同網域（那是系統票核過的）；每 IP 每 10 分鐘 60 次、全域 300 次。
**這不是系統票**——票還是代理投的，`evidence_url` 放那個網址；判定紀錄讓對帳看得到票背後的第二來源。
參考實作 `scripts/agent/relay_jev_verify.py`：不帶任何金鑰，/next → 搜尋（DuckDuckGo lite）→ judge → 投票；
真的小模型只需要決定搜尋關鍵字。紅線：不能拿 Jev 對「提交的那一頁」的判定當代理票。

管線：cron 每 10 分 → `system-one?action=precheck` → 撿 pending 且沒判過的 → 抓第一個 source_url（帶瀏覽器 UA）→ Jev → 寫
`jev_decisions(contribution, source_support)` → 重算共識。抓不到正文的一樣留一列（cannot_tell、機率 0、model `policy-tw/fetch-only-*`），
對帳時才分得出「來源抓不到」與「Jev 看不出來」。

### 3-2 不碰需要出去查證的事

`verify`、`adjudication`、任何 `task` 的查證，本體就是「把證據找回來」。不碰。

### 3-3 不進 `contribution_votes`

那張表有 `agent_name` 與 `verifier_ip_hash`，硬塞會污染 `tallyByIp` 去重、貢獻榜計分、
以及 24 小時自驗排除。要獨立欄位或獨立表。

## 4. 四個運用面

判準：**證據是不是已經在我們資料庫裡**。是 → 可以；要出去找 → 不行。

### 4-1 身份指認衝突（唯一建議現在就接進流程的）

**作用**：skill.md §2-11 規定 `ambiguous` 時兩票指不同的人（一票 `new`、一票某人也算不同）
→ 整筆轉 `disputed` → 開一個要 **4 票** 的裁決任務。這個升級跟來源無關：候選人的政黨、縣市、
出生年、參選紀錄全都已經在資料庫裡，代理也只是在比對這些欄位。

改成：衝突時先問 Jev，機率 ≥0.95 就用它定案，低於就照舊升級。
**這不是把 2 票變 1 票，是把 4 票裁決變成 0 票。**

**需要放進 state 的資料**

| 欄位 | 來源 | 不給會怎樣 |
| --- | --- | --- |
| `incoming` | 貢獻 payload 的姓名／政黨／縣市／出生年／參選層級／現職 | — |
| `existing[]` | 每個候選人的 `politicians` 整列（含 `birth_year`、`current_position`、`education_level`） | 只給 `politician_keys` 的比對結果會判錯，那是分數不是事實 |
| criteria | 候選人 id 前 8 碼 → 一行描述，外加 `new` | — |
| instructions | 要寫明「無黨籍及未經政黨推薦＝無黨籍」「現職一個寫任期一個寫參選紀錄不代表不同人」 | 不寫的話政黨異寫會被當成矛盾 |

**實測**（2026-09-19，`politician_identity_reviews` 全部 13 筆，一筆一呼叫）

| 結果 | 筆數 |
| --- | --- |
| 機率 ≥0.91 | 11 |
| 低信心（蘇清泉 0.78／信心 0.56、黃捷 0.67／信心 0.34） | 2 |

那兩筆低信心的 `incoming` 只有姓名和一個**互相矛盾**的政黨（無黨籍 vs 中國國民黨／民主進步黨），
其他欄位全 null。唯一可比的欄位在打架，給低信心是對的——**它的信心值有校準，這比答案本身更有用**。

⚠️ 這 13 筆 `resolved_politician_id` 全是 null，**沒有人工答案可以對**，所以拿不到一致率。
影子欄位就是為了讓下一批有得對。

### 4-2 同名重複人物掃描（批次，唯讀）

**作用**：15,889 位政治人物裡找出同一個人被建成兩筆的。同名分組後兩兩比對。

**實測**：152 個同名組、164 對，判為同一人 17 對，成本 $0.0041。
清單見附錄。

**但這裡的發現比結果重要**：17 對裡前 15 對全是同一個模式——

```
吳品叡  無黨籍，嘉義縣，1986        | 無黨籍及未經政黨推薦，嘉義縣，1986
葉國文  台灣民眾黨，新竹市，1972    | 民眾黨，新竹市
洪和成  無黨籍及未經政黨推薦，金門縣 | 無黨籍，金門縣
```

政黨異寫 + 一邊有出生年一邊沒有。而 `identity-normalize.ts` 的 `PARTY_ALIASES`
**早就**有 `民眾黨→台灣民眾黨`、`無黨籍及未經政黨推薦→無黨籍`。這些不需要 AI，
是既有規則該接住卻沒接住的：政黨對上了也只算 `strength 1`（弱面向），分數 1 就落進 `ambiguous`，
正好就是那 13 筆 review 的同一句「唯一候選但只有弱面向命中（分數 1）」。

**所以第一件該做的事不是接 Jev，是決定「同名＋同縣市＋政黨正規化後相同」要不要升成 strength 2。**
那 12 對不花錢就解決。

Jev 真正的價值在剩下三對，規則絕對判不出來的：

```
0.91  何志勇  中國國民黨，新竹市，1980  | 無黨籍，新竹市
0.89  陳重嘉  無黨籍，彰化縣            | 台灣民眾黨，彰化縣，1981
0.64  李國璋  中國國民黨，新竹市        | 台灣民眾黨，新竹市，1970
```

政黨真的不同——可能換黨，也可能兩個人。李國璋新竹市有三筆，Jev 把「台灣民眾黨 vs 民眾黨」
判 0.98 同一人、把「中國國民黨 vs 那兩筆」判 0.64/0.51，這個分寸是對的。

⚠️ 合併是破壞性的，`merge-politicians` 一律要人點頭。

### 4-3 政見三判定（影子模式）

對同一筆政見一次問三題（見 2-2）。

**需要放進 state 的資料**

| 題目 | state 必備 | 沒有會怎樣 |
| --- | --- | --- |
| 非政見 | `target.title` + `target.description` | — |
| 排重 | `others` = 同一人其他政見的 title + description（description 截 200 字） | 只給 title 判不出「同一件事換句話說」 |
| 斷年度 | `elections` = 該人參選紀錄；**`already_labelled` = 該人已標屆別的政見** | 見 2-3，5/8 vs 8/8 |

**實測**（蘇巧慧 26 筆政見裡沒有屆別的 8 筆）

| 判定 | 結果 | 評價 |
| --- | --- | --- |
| 非政見 | 7 筆 `policy`（0.95–1.00）；「六大福利政見」判 `not_policy`（1.00） | 可用。那筆描述是「勾勒新北未來的發展方向」，確實是包裹式標題 |
| 斷年度 | 給參考資料後 8/8 全對，5 筆 ≥0.90 | 可用，但一定要餵 `already_labelled` |
| 排重 | 7 筆 `none`，1 筆誤報（六大福利政見 → 步道纜車 0.64） | 要靠門檻，見下 |

另一組對照（3 筆真實政見 + 1 筆口號「母雞帶小雞 - 最強新北隊」）：4/4 全對，0.97–1.00。
其中「讓年輕人創業不孤單」這種很虛的仍判 `policy`(0.98)，跟 `policy-likeness.ts`
「真政見不該被擋在門外」的立場一致。

### 4-4 排重的門檻

把四輪測試的機率攤開：

| 類型 | 機率 |
| --- | --- |
| 真重複（人工改寫三筆） | 1.00 / 1.00 / 1.00 |
| 真重複（子集，少講一項） | 0.99 |
| 真重複（同標題） | 0.97 |
| 真不重複（主題近、事情不同） | `none` 0.93 |
| 真不重複（同主題不同對象） | `none` 0.92 |
| **誤報**（六大福利政見 → 步道纜車） | **0.64** |
| 真的有爭議（新生兒補助 8 萬 vs 既有 10 萬） | `none` 0.58 |

真重複全部 ≥0.97，誤報 0.64，中間是空的。**門檻 0.95**。

兩個限制：

1. **只接 `choice != none` 那一邊。** 它說「不重複」的可信度沒被獨立測過，
   不能拿來當「保證不重複」用。
2. **只能當候選，不能當結論。** skill.md §2-10 規定代理看到重複就投 `disagree`，
   所以一個假的重複標記會直接殺掉一筆真政見，而漏掉一筆重複只是維持現狀——代價完全不對稱。
   它應該跟現有相似度算法並列進 `current.similar_policies`，標明來源是機器判斷。

⚠️ 樣本只有 10 筆，而且改寫是人工寫的，可能比真實的近似重複容易。

## 5. 要存什麼（稽核）

每一次呼叫都要留下能回答「當初為什麼這樣定案」的東西：

| 欄位 | 為什麼 |
| --- | --- |
| `jev_model` | 存 `typesafe/jev-1.13-20260917`（回應裡的，不是請求裡的）。換版後重問要開新紀錄，不能覆蓋 |
| `jev_choice` / `jev_probability` | 答案與機率 |
| `jev_state` | 它當時看到的 state 原文。少了這個，事後無法重現，也查不出是資料不足還是判斷錯 |
| `jev_asked_at` | — |
| `usage.cost` | 寫進 `ai_usage_logs` |

**一次性要真的是一次性**：同一筆、同一種判定只問一次並寫死。
實作上很容易變成每次 `/next` 都重問一遍，那就退化成可以重骰到滿意為止。

## 6. 落地順序（更新於 2026-09-19 晚）

| # | 項目 | 狀態 |
| --- | --- | --- |
| 1 | 政黨面向要不要從 strength 1 升到 2（4-2） | 待裁。不花錢，解掉 12 對重複人物 |
| 2 | 影子紀錄：表、端點、觸發、補漏、滾動 | **已上線**（§7） |
| 3 | 斷年度 31 筆：用優先序讓代理先做，不透露答案 | **已上線**。代理回報後 `system_one_accuracy` 會出現第一批真正的準確率 |
| 4 | 身份衝突免升級（4-1） | 等 3 累積夠 |
| 5 | 同名重複人物 → `duplicate_politician` 任務 → 多 AI 查證 → 軟合併 | 待建。前提是把 `merge-politicians` 從「按姓名硬刪」改成「按配對軟合併」（見下） |

**不做**：把 Jev 的答案當 hint 塞進 `/next` 給代理看——錨定效應會讓對帳失去意義。

### 6-1 `merge-politicians` 現況（2026-09-19 查）

不能當執行器：`{ name }` 進去把該姓名**全部**合成一筆（李國璋新竹市三筆裡 Jev 判其中一筆是不同人）；
`.delete()` 硬刪，沒有 `edit_history`、沒有還原路徑——比 `removal` 破壞性強卻一票不用，只要管理金鑰；
`politician_elections` 轉移前沒去重。要改成：兩個 id 的配對、敗方標 `merged_into` 留著、寫 `edit_history`、
轉移前去重。門檻 `high`（4/6/8）——判錯會抹掉一個真實存在的人。

### 8-1 Jev 不是決定性的，但雜訊全在門檻底下

## 9. 這一輪的誠實標註

- **第一批 450 筆的 `state` 跟線上 TS 組法不一樣。** 第一版腳本沒存 state，寫入時從凍結快照重建；

  `state_hash` 舊 `6096f739…` 新 `19faf02b…`——**第一批的 hash 不能跟之後的比**。影響只有一個：
  `retry_election` 第一次重問舊批次的政見時 unique 不會擋（hash 不同），成本由候選規則兜住。之後全走 `system-one`，這個問題不會再長。
